# create: HTML レポートを作る

依頼文と素材から、`frontend-design:frontend-design` の指針に沿った HTML レポートを 1 ファイルで作り、保存する。次の手順 1〜8 を順に行う。

## 環境の判定方法（`/report-studio:doctor` と共通）

- Playwright MCP: `mcp__playwright__browser_navigate` などのブラウザツールが、利用可能なツールの一覧、または ToolSearch で見つかれば「使える」。`mcp__claude-in-chrome__*` は対象外。
- `frontend-design`: 利用可能なスキルの一覧に `frontend-design:frontend-design` があれば「使える」。
- `dataviz`（任意）: スキルの一覧にあれば、グラフを描くときにその指針に従う。なくても動く。
- この判定は推定である。実行時に使えなかったら、その時点で止める。

## 手順

1. **環境の確認**: 上の判定で、Playwright MCP と `frontend-design` の両方が「使える」か確かめる。どちらかが使えなければ、HTML を作らずに止まる。次を伝える: 「使えないもの」「`/report-studio:doctor` で点検できること」「README の導入手順を見ること」。簡易な生成で代用しない。

2. **依頼の受け取り**: 起動時の依頼文を起点にする。依頼文に書かれたファイルのパスは、前後の引用符を外して存在を確かめ、読み込んで素材にする。Markdown・CSV・テキスト・画像（PNG/JPG）を基本とし、Excel などは関連スキルで読める範囲で読む。読めなかったファイルは、その旨を伝え、読めた素材だけで続ける。会話の内容を素材にすることはしない。

3. **不足の補完**: 次の 4 項目のうち、依頼文と素材から分からないものだけを AskUserQuestion で聞く。推測で埋めない。
   - 目的（レポートの種類は目的で兼ねる）
   - 読み手
   - 必須の内容
   - 分量

   1 回に聞くのは最大 4 問。分からない項目がなければ、聞かない。

4. **デザイン方向の提示**: 内容と読み手に合う方向性を 2〜3 案出し、AskUserQuestion の選択肢で選んでもらう。各案は、トーン・配色・書体・レイアウトの考え方を 1〜2 行で書く。依頼文に配色やトーンの希望があれば、案に反映する。どれも合わないときは、「その他」の自由記述を受けて案を作り直す。

5. **生成**: 選ばれた方向で `frontend-design:frontend-design` スキルを呼び出し、その指針に沿って HTML を作る。呼び出すとき、次の 3 つを渡す。
   - 選んだデザイン方向
   - 素材（本文・表・データ・画像）
   - 下の「HTML の仕様」の制約

   `frontend-design` の指針が制約（1 ファイル完結・外部依存なし・システムフォント）と衝突するときは、制約を優先する。構成は依頼内容ごとに毎回設計し、固定のテンプレは使わない。素材の文字列は、埋め込む場所ごとにエスケープする。HTML の本文・属性では `& < > "` を実体参照にし、`<script>` 内の JS のデータでは `<` を `\u003c` にする（`</script>` で途中終了させない）。素材に `<script>` などが含まれていても実行されないようにする。素材が大きいとき（数千行の CSV など）は、読む前に行数を確かめる。1000 行を超えるときは、全件を読み込まず、Python などで集計・要約した結果だけを載せる。数値は素材と照合し、素材にない内容は補わない。照合は表・グラフだけでなく、本文中の数値や「〇月以降」「最高」「最低」といった期間・順位の記述にも行う。文章中の数値は、書く前にコードで計算し、その結果を、対象の月・範囲の名前とあわせて書く（例: 「8月以降は毎月148万円以上」は、8月以降の最小値を計算して書く）。

6. **保存**: 利用者が実行したときのカレントフォルダ直下に、`YYYY-MM-DD-題名.html` で保存する。
   - 題名は依頼内容から付ける（日本語可、最大 40 文字）。`\ / : * ? " < > |` は取り除く。空になったら `report` にする。
   - 同名のファイルがあるときは、上書きしてよいか聞く。「いいえ」なら、末尾に連番を付けた別名（`-2`, `-3`…）で保存する。連番の名前も既にあるときは、空いている最小の番号まで進める。
   - 書き込めないときは、保存先を聞く。

7. **検証**: Playwright MCP で、保存した HTML を `file://` で開く。
   - 幅 1280px と 375px のスクリーンショットで、崩れ（はみ出し・重なり・文字化け）がないか確かめる。
   - 印刷表示（`browser_emulate_media` の print）にして、`browser_evaluate` で `document.documentElement.scrollWidth` が `clientWidth` を超えないこと（横方向のはみ出しがない）を確かめる。
   - 崩れがあれば直して、もう一度確かめる。修正は最大 3 回までとし、残ったら完了報告に書く。
   - `file://` が開けない設定のときは、止まって設定（`--allow-unrestricted-file-access` など）を案内する。

8. **完了報告**: 次の 3 点を伝える。
   - 保存先の絶対パス
   - 決めたデザイン方針（1〜2 行）
   - 検証の結果（見た画面幅と、直した点）

   素材の内容が HTML にそのまま入っているので、共有する前に機密情報を確かめるよう添える。レポートの修正は、同じ会話で同じファイルを通常の編集で直す。

## HTML の仕様

- 1 ファイルで完結する。CSS・JS・SVG をインラインに書く。外部 CDN・Web フォント・外部画像を読み込まない。
- 画像（PNG/JPG）は base64 でインライン化する。大きい画像は縮小するか、利用者に確認する。
- グラフはインライン SVG／CSS で描く。`dataviz` スキルが使えるときは、その指針に従う。
- 言語は依頼文に合わせる。フォントはシステムフォントを指定する（日本語なら日本語に適したシステムフォントのスタック）。
- `@media print` の CSS を常に入れる。可読性と印刷適性を、見た目の個性より優先する（印刷で消える背景色に頼らない）。
- ダークモード対応は、依頼文にあるときだけ入れる。
