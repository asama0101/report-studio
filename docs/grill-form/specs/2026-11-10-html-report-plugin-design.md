# report-studio 設計

## 概要
利用者が希望した内容で、デザインされた HTML レポートを生成する Claude Code プラグイン `report-studio` を作る。見た目は `frontend-design:frontend-design` スキルの指針で設計する。

### 入力
- 依頼文: 「frontdesignを使いつつ、利用者が希望した内容でHTMLのレポート生成するプラグイン・スキルを開発したい」
- 入力ファイル: なし（参考資料の指定なし）

### 構成
- 開発場所: `D:\claude\local-repo\xxx\`（現在の作業フォルダ）自体をプラグインのルートにする。直下に `.claude-plugin\plugin.json`、`skills\create\SKILL.md`、`commands\doctor.md`、`README.md` を置く。git 管理は現時点でなし。
- プラグイン名 `report-studio`。スキル `report-studio:create`（起動: `/report-studio:create 〇〇のレポートを作って`）。
- コマンド `/report-studio:doctor`: 動作に必要な環境を点検して、結果を一覧（箇条書き）で報告する。点検のみで、インストールや設定の変更はしない。
- 環境の判定方法（`create` と `doctor` で共通）: Playwright MCP は、`mcp__playwright__browser_navigate` 等のブラウザツールが ToolSearch または利用可能なツール一覧で見つかるかで判定する（`mcp__claude-in-chrome__*` は対象外）。`frontend-design` は、利用可能なスキル一覧に `frontend-design:frontend-design` があるかで判定する。`dataviz` スキルは任意で、スキル一覧にあれば使う。判定は推定であり、実行時に使えなければその時点で止める。
- ローカルでの使い方: `claude --plugin-dir D:\claude\local-repo\xxx` で読み込んで使う。手順は README に書く。配布（マーケットプレイス・GitHub）はしない。

## 流れ（`create` スキル）
1. 環境の確認: 上記の判定で、Playwright MCP と `frontend-design` が使えるか確認する。どちらかが使えなければ、HTML を作らずに止まり、`/report-studio:doctor` と README の導入手順を案内する（簡易生成はしない）。
2. 依頼の受け取り: 起動時の依頼文を起点にする。依頼文に書かれたファイルのパスは読み込んで素材にする。Markdown・CSV・テキスト・画像（PNG/JPG）を基本とし、それ以外（Excel など）は、関連スキルで読める範囲で読む。読めなかったファイルは、その旨を伝え、読めた素材だけで続ける。会話の内容を素材にする機能は持たない。
3. 不足の補完: 目的・読み手・必須の内容・分量（種類は目的で兼ねる）のうち、依頼文と素材から分からないものだけを AskUserQuestion で聞く。推測で埋めない。1 回に聞くのは最大 4 問。不足がなければ聞かない。
4. デザイン方向の提示: 内容と読み手に合う方向性（トーン・配色・書体・レイアウトの考え方）を 2〜3 案、AskUserQuestion の選択肢で出し、選んでもらう。依頼文に配色・トーンなどの希望があれば、案に反映する。どれも合わなければ、「その他」の自由記述を受けて案を作り直す。
5. 生成: 選ばれた方向で `frontend-design:frontend-design` スキルを呼び出し、その指針に沿って HTML を作る。呼び出すとき、選んだ方向、素材、「HTML の仕様」の制約を渡す。`frontend-design` の指針が制約（1 ファイル完結・外部依存なし）と衝突するときは、制約を優先する。構成は依頼内容ごとに毎回設計する（固定テンプレは持たない）。素材は HTML に埋め込むときにエスケープする。素材が大きいとき（数千行の CSV など）は、集計・要約して載せる。数値は素材と照合し、素材にない内容は補わない。
6. 保存: 利用者が実行したときのカレントフォルダ直下に `YYYY-MM-DD-題名.html` で保存する。題名は依頼内容から Claude が付け（日本語可、最大 40 文字）、`\ / : * ? " < > |` は取り除く。空になったら `report` にする。同名ファイルがあれば、上書きしてよいか聞き、「いいえ」なら別名（末尾に連番 `-2`, `-3`…）で保存する。書き込めないときは、保存先を聞く。
7. 検証: Playwright MCP で `file://` のページを開き、幅 1280px と 375px のスクリーンショットで崩れ（はみ出し・重なり・文字化け）を確認し、あれば直す（修正は最大 3 回）。印刷表示（`browser_emulate_media` の print）でも横方向のはみ出しがないか確認する。
8. 完了報告: 保存先の絶対パス、決めたデザイン方針（1〜2 行）、検証の結果（見た画面幅と、直した点）を伝える。レポートの修正は、同じ会話で同じファイルを通常の編集で直す。

## HTML の仕様
- 1 ファイルで完結する。CSS・JS・SVG をインラインに書き、外部 CDN・Web フォント・外部画像を読み込まない。画像（PNG/JPG）は base64 でインライン化する（大きい画像は縮小するか、利用者に確認する）。
- グラフはインライン SVG／CSS で描く。`dataviz` スキルが使える環境では、その指針に従う。
- 言語は依頼文に合わせる。フォントはシステムフォントを指定する（日本語なら日本語に適したシステムフォントのスタック）。
- 印刷・PDF 出力に耐える `@media print` の CSS を常に入れる。可読性と印刷適性を、見た目の個性より優先する。ダークモード対応は、依頼文にあるときだけ入れる。

## 受入条件
1. `D:\claude\local-repo\xxx\` 直下の `.claude-plugin\plugin.json` が `name: report-studio` で有効な JSON である。`claude --plugin-dir D:\claude\local-repo\xxx` で起動すると、スキル `report-studio:create` とコマンド `/report-studio:doctor` が `/help` の一覧に出る。
2. 目的・読み手・内容・分量が分かる依頼文で `/report-studio:create` を実行すると、質問なしでデザイン方向の選択に進み、選択後に、カレントフォルダ直下に `YYYY-MM-DD-題名.html` が 1 つできる。依頼文に不足があるときは、不足分だけが聞かれる。
3. できた HTML は、`src`・`href`・`@import`・`url()` に `http://`・`https://` で始まる外部の読み込みを含まない（SVG の `xmlns` 宣言と、本文中のリンク `<a href>` は除く）。
4. 依頼文に書いたファイルパス（CSV・Markdown・画像）の内容が、レポートの本文に反映されている。
5. 質問で答えた目的・読み手・内容・分量と、選んだデザイン方向が、HTML の内容と見た目に反映されている。
6. 印刷表示（`emulateMedia` の print）で、`scrollWidth` が `clientWidth` を超えない（横方向のはみ出しがない）。HTML に `@media print` が含まれる。
7. 同名のファイルがあるとき、確認なしに上書きしない。「いいえ」と答えると、連番の別名で保存される。
8. Playwright MCP または `frontend-design` が使えない環境で `/report-studio:create` を実行すると、HTML を作らずに止まり、`/report-studio:doctor` と README の導入手順を案内する。README に、`--plugin-dir` での使い方、Playwright MCP の登録方法、`frontend-design` の導入方法が書かれている。
9. `/report-studio:doctor` が、Playwright MCP のブラウザツール、`frontend-design` スキル、`dataviz` スキル（任意）について、使える／使えない（任意項目は「未導入でも動く」）を箇条書きで示す。使えない項目には、README の該当箇所への案内が付く。
10. 完了報告に、保存先の絶対パス、デザイン方針、検証の結果（見た画面幅と、直した点）が含まれる。

確認は、サンプルの依頼文と CSV を用意した手動のシナリオで行う。環境のない状態（受入条件 8）は、Playwright MCP を無効にして起動することで作る。

## 非目標
- 固定のレポートテンプレ・型の提供。
- 会話の内容を素材にする機能。
- レポート作成後の修正専用の手順（作成中の検証による自動修正は範囲内）。
- Chart.js 等の外部ライブラリの利用、Web フォントの読み込み。
- マーケットプレイスでの配布、GitHub での公開、git 管理の整備。
- PDF・PowerPoint など HTML 以外の形式の生成。
- 必要な環境（Playwright MCP、`frontend-design`）のインストールや設定の自動変更。
- 複数ページ・複数ファイルのサイト生成、フォーム送信・サーバー連携などの双方向機能。
- 大量データの全件掲載、統計処理そのもの。
- アクセシビリティの網羅的な保証、日本語・英語以外の言語、他の OS・端末での見え方の保証。

## リスク
- `frontend-design` の指針が更新されると、出力の傾向が変わる。スキル呼び出しで追従する方針なので、受け入れる。
- 必須の前提が 2 つ（Playwright MCP、`frontend-design`）あるため、未導入の環境では何も作れない。`doctor` と README で補う。環境の判定は推定で、実行時の失敗でも止まる。
- ブラウザ検証は、作成した PC の 1 環境でのスクリーンショットの確認で、機械的な判定ではない。Playwright MCP が `file://` を開けない設定のときは検証が成り立たないので、止まって設定を案内する。
- 質問（不足補完とデザイン方向の選択）が毎回入るため、軽い依頼でも往復が増える。
- 素材の機密情報（個人情報・社外秘）が HTML にそのまま残る。保存した HTML の取り扱いは利用者の責任とし、完了報告で素材の内容が含まれる旨を伝える。
- 数値の集計ミス・素材にない内容の補完が起こり得る。数値は素材と照合し、補わない方針だが、保証はしない。
- 保存先がカレントフォルダ直下なので、同期フォルダ（OneDrive など）やリポジトリ内で実行すると、成果物が混ざる。
- `frontend-design` の指針が React やフレームワーク向けの内容を含み得るため、制約（1 ファイル完結・外部依存なし）を渡して優先させる。

## 決定ログ
- Q1: プラグイン 1 つ + スキル 1 つ。
- Q2: 依頼文（引数）+ 不足分の質問 + ファイル読込。会話内容の読み込みは選ばれなかったので、非目標にした。
- Q3: `frontend-design:frontend-design` を Skill 呼び出しで使う。
- Q4: 1 ファイル完結、外部 CDN なし。
- Q5: 利用者のカレントフォルダに保存する（`reports/` は切らない）。
- Q6: スクリーンショットで検証し、崩れを直す。
- Q7: このフォルダで開発し、ローカルで使う。
- Q8: テンプレなし。依頼ごとに毎回設計する。
- Q9: 毎回 2〜3 案のデザイン方向を出して選んでもらう。
- Q10: グラフはインライン SVG／CSS。`dataviz` があればその指針に従う。
- Q11: 言語に合わせたシステムフォント + 印刷 CSS。ダークモードは依頼文にあるときだけ。
- Q12: プラグイン `report-studio` / スキル `report-studio:create`。
- Q13・Q14: 現在のフォルダ `D:\claude\local-repo\xxx\` 自体をプラグインのルートにする。
- Q15: 同名ファイルがあれば、上書きしてよいか聞く。
- Q16: 検証ツールがなければ止まって案内する。点検用の `doctor` コマンドを用意する。
- Q17: 修正は通常の編集で行い、スキルは初回作成に集中する。
- Q18: doctor と Playwright 必須（なければ止まる）を、決定どおり残す（レビューのシンプル化案は不採用）。
- Q19: 画像素材は base64 でインライン化する。
